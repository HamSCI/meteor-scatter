# meteor-scatter in F32 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** meteor-scatter decodes MSK144 from F32 audio made from one F32 I/Q channel, and keeps the I/Q of every decoded slot.

**Architecture:** jt9 (the UberSDR MSK144 port) learns to read a mono 32-bit float WAV for MSK144. meteor-scatter switches each channel from radiod's `usb` preset to `iq`, makes the real USB audio from the I/Q, and writes it for jt9 as F32 without rounding. When jt9 decodes something, meteor-scatter keeps the slot's I/Q as a two-channel F32 WAV. A per-instance config key chooses between the old path and the new, so both can run side by side before the switch.

**Tech Stack:** C++17 (ubersdr_wsprd, the `msk144` branch), Python 3.11 + numpy (meteor-scatter), ka9q-python.

**Spec:** meteor-scatter `docs/superpowers/specs/2026-11-06-f32-iq-design.md` (c174000, 4ecc8e2).

## Global Constraints

- Float scale, as the port already uses for FT8/FT4/FT2/FST4W: full scale is 1.0, and a 16-bit sample `s` is `s/32768`. A float file built from 16-bit samples must decode byte for byte like the 16-bit file.
- jt9's 16-bit MSK144 path keeps byte-for-byte parity with WSJT-X 3.2.0-rc1: `jt9-compare` stays at 395 of 395, `./build.sh --check` passes, and the five piece checks stay identical.
- A float WAV for MSK144 is accepted only by our port. WSJT-X 3.0.2's jt9 refuses one. meteor-scatter writes F32 audio only when the resolved jt9 lists `--msk-shmsg` in its `-h` (our port does, and 3.0.2 doesn't). Otherwise it writes 16-bit, as now.
- The I/Q channel uses the `iq` preset at 12000 Hz complex, F32, AGC off, gain 0 dB, with filter edges +50 Hz to +3000 Hz relative to the dial frequency, the `usb` preset's passband.
- Slots last 15 s (`tr_period_sec`, unchanged). meteor-scatter keeps a slot only when jt9 decodes something.
- A kept I/Q file is a two-channel `WAVE_FORMAT_IEEE_FLOAT` WAV, 32-bit, channel 1 = I, channel 2 = Q, at the channel's sample rate. It keeps radiod's scale, with no gain and no normalisation. The JSON sidecar beside it gains `"capture": "iq"`, `"iq_sample_rate"`, `"iq_encoding": "f32le"`, `"iq_center_hz"` and `"iq_filter_hz": [50, 3000]`.
- The config key `[radiod.msk144] capture = "usb" | "iq"` defaults to `"usb"` until the side-by-side proof passes.
- Repos: meteor-scatter develops on `main`. ubersdr_wsprd works on the `msk144` branch, after the LDPC speed-up (speed-2) lands. Nothing is pushed without Michael's word.

## Review Focus

1. A slot whose I/Q holds NaN or inf (radiod glitch, stream restart) → jt9 must not crash or loop, and meteor-scatter logs it once (Task 1 `msk144-float-nan`; Task 3 `test_nonfinite_iq_slot`).
2. A very low-level F32 slot (radiod output around −135 dBFS) decodes as well as the same slot peak-normalised (Task 2 `test_f32_audio_keeps_gain`; Task 1 `msk144-float-level` case).
3. A stream that drops mid-slot → the I/Q gap is zero-filled, as the audio path does now, and the kept I/Q file's sample count stays exact (Task 3 `test_iq_gap_zero_filled`).
4. The resolved jt9 is WSJT-X 3.0.2 (a station without the port) → meteor-scatter keeps writing 16-bit audio and decodes as today, even with `capture = "iq"` (Task 2 `test_falls_back_to_s16_for_302`).
5. The MSQP archive cap (`archive_max_gb`) still holds with files four times larger (Task 3 `test_archive_cap_counts_iq_bytes`).
